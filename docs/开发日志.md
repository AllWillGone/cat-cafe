## 数据库设计

### 表结构（6 张表）

| 表名 | 说明 | 关键字段 |
|------|------|----------|
| user | 用户 | userType: 0=顾客, 1=管理员 |
| catinformation | 猫咪信息 | status: 0=休息中, 1=在岗中 |
| product | 商品 | category: 0=服务 1=餐饮 2=猫咪用品, status: 0=下架 1=在售 |
| orders | 订单 | batchNo 批次号, orderStatus 五态, 用户名手机号快照 |
| comment | 评论 | targetType: 0=商品 1=猫咪, auditStatus: 0=待审核 1=已通过 2=已拒绝 |
| likes | 点赞 | likeType: 0=商品 1=评论 2=猫咪, 联合唯一索引防重复点赞 |

### 相对原始设计的结构变更

- **product 表 — 新增字段**
  - 新增 `status TINYINT`
  - 原因：支持上架(1) / 下架(0)。有历史订单时不能直接删商品，先下架隐藏

- **orders 表 — 新增字段**
  - 新增 `batchNo VARCHAR(32)`
  - 原因：多商品下单时同一批次共用，支持聚合展示、批量取消/支付

- **comment 表 — 字段替换**
  - 删除 `catid`，替换为 `targetType` + `targetId`
  - 原因：一张表同时评猫咪(targetType=1)和商品(targetType=0)，和 likes 设计统一

- **comment 表 — 移除约束**
  - 移除外键 `FK → catinformation`，改为软引用
  - 原因：targetId 可能指向 product 或 catinformation，无法建单一外键

### 各文件作用

- **`.env`** — 存八条配置：数据库五条（地址、端口、用户名、密码、库名）+ JWT 三条（密钥 `JWT_SECRET`、算法 `JWT_ALGORITHM`、过期时间 `JWT_EXPIRE_HOURS`）。写在这里而不是代码里，被 `.gitignore` 排除，不会泄露到 GitHub。

- **`config.py`** — 用 `python-dotenv` 读取 `.env` 文件内容，按 `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` 拼接数据库连接字符串，同时读取 JWT 密钥和算法配置，供 `database.py` 和 `auth.py` 使用。

- **`database.py`** — 核心连接模块：
  - `engine`：全局唯一的数据库引擎（连接池），程序启动时创建一次，所有请求共用
  - `SessionLocal`：会话工厂，每次请求"取号"拿一个新会话，用完归还
  - `Base`：ORM 基类，`models.py` 中所有表模型都继承它
  - `get_db()`：FastAPI 依赖注入函数，请求进来创建会话，结束自动关闭

- **`main.py`** — FastAPI 应用入口：
  - 创建 `FastAPI` 实例（`title="猫咖点单系统"`）
  - 包含 `/health` 健康检查 + 通过 `include_router` 注册 6 个路由模块（user/cat/product/order/comment/likes）
  - 启动命令：`uvicorn main:app --reload`
  - 建表方式：采用 `init.sql` 手动建表，不调用 `create_all`。原因 —— `@app.on_event("startup")` 已弃用；`init.sql` 作为权威建表文档，组员无需安装 Python 也能查看；保证数据库结构完全可控

- **`models.py`** — ORM 模型层，6 个类对应 6 张表（`User` / `Catinformation` / `Product` / `Order` / `Comment` / `Likes`）。每个类属性一对一映射数据库字段（camelCase）：

  | SQL 类型 | Python Column |
  |----------|---------------|
  | `BIGINT UNSIGNED` | `BigInteger` |
  | `VARCHAR(n)` | `String(n)` |
  | `TEXT` | `Text` |
  | `DECIMAL(10,2)` | `Numeric(10, 2)` |
  | `DATE` | `Date` |
  | `DATETIME` | `DateTime` |
  | `NOT NULL` | `nullable=False` |
  | `DEFAULT 0` | `default=0` |
  | `DEFAULT CURRENT_TIMESTAMP` | `server_default=func.now()` |
  | `PRIMARY KEY` | `primary_key=True` |
  | `UNIQUE` | `unique=True` |
  | 外键约束 | `ForeignKey("表.字段")` |

  两个关键概念：
  - **`Foreign Field`**：数据库层面的硬约束，对等 init.sql 的 `CONSTRAINT ... FOREIGN KEY ... REFERENCES`。阻止插入不存在的关联 ID，`ondelete="RESTRICT"` 阻止删有关联数据的记录
  - **`relationship`**：Python 层面的快捷方式，不产生数据库字段。用来在代码中链式访问关联对象 —— `order.user.userName`（订单 → 用户 → 用户名），`user.orders`（用户 → 他的所有订单），避免每次手写 JOIN

  注意：`models.py` 不负责建表。建表统一用 `database/init.sql`，`models.py` 仅做运行时映射。

- **`schemas.py`** — Pydantic 数据校验模型，定义每个接口的请求格式和响应格式。`ConfigDict(from_attributes=True)` 使其可直接从 ORM 对象读取属性，省去手动 `.model_dump()`。

- **`auth.py`** — JWT 认证模块，三个函数：

  | 函数 | 作用 | 触发时机 |
  |------|------|----------|
  | `create_access_token(data)` | 把用户 ID 打包成加密 token 字符串 | 登录成功后调用 |
  | `get_current_user(db, token)` | 从请求头取 token → 解码验签 → 查库返回用户 | 需要登录的接口用它做依赖 |
  | `get_current_admin(current_user)` | 在 get_current_user 基础上检查 userType=1 | 管理员接口用它做依赖 |

  工作流程：客户端登录 → 服务器返回 token → 客户端存起来 → 后续请求带 `Authorization: Bearer <token>` → `get_current_user` 自动解析校验。token 含签名，防篡改；含过期时间，默认 24 小时。

## 错误码一览

| 状态码 | 含义 | 触发场景 |
|--------|------|----------|
| 200 | 成功 | 注册/登录正常 |
| 400 | 请求有误 | 原密码错误、不能删除自己、订单状态不允许修改、存在未完成或不可删除订单导致无法注销 |
| 401 | 未认证 | token 缺失/无效/过期、用户名密码错误 |
| 403 | 无权限 | 非管理员访问管理员接口、非作者删评论/取消点赞 |
| 404 | 不存在 | 请求的资源不存在、点赞对象不存在 |
| 409 | 冲突 | 重复点赞 |
| 422 | 请求数据不合规 | 用户名已存在、字段为空、长度超限 |
| 500 | 服务器内部错误 | 数据库未启动 |


### POST /api/register — 用户注册

- **请求**：`{ "userName": "str", "userPassword": "str" }`
- **响应**：`{ "userId": int, "userName": "str", "userType": 0, "registerTime": datetime, "token": str }`
- **错误**：422 `"用户名已存在"`
- **说明**：密码 bcrypt 哈希存储，默认注册为顾客(userType=0)。注册成功直接返回 JWT token，无需再登录


### POST /api/login — 用户登录

- **请求**：`{ "userName": "str", "userPassword": "str" }`
- **响应**：`{ "userId": int, "userName": "str", "userType": int, "registerTime": datetime, "token": str }`
- **错误**：401 `"用户名或密码错误"`
- **说明**：`pwd_context.verify()` 比对密码，不存在和密码错统一返回 401（防用户名枚举）。成功后返回 JWT token，后续请求带 `Authorization: Bearer <token>`


### GET /api/user/me — 查看当前用户信息

- **请求**：无请求体，需在请求头带 `Authorization: Bearer <token>`
- **响应**：`{ "userId": int, "userName": "str", "userType": int, "gender": int|null, "birthday": date|null, "registerTime": datetime }`
- **错误**：401 token 缺失/无效/过期
- **说明**：token 由 `get_current_user` 自动解析校验，返回当前登录用户的完整信息


### PUT /api/user/me — 修改个人信息

- **请求**：`{ "userName"?: str, "gender"?: int(1或2), "birthday"?: date }`  全部可选，传什么改什么
- **响应**：同 GET /api/user/me
- **错误**：401 未登录，422 用户名已被占用
- **说明**：不传的字段保持原值不变。改用户名时会检查是否和别人重复


### PUT /api/user/me/password — 修改密码

- **请求**：`{ "oldPassword": "str", "newPassword": "str(6-128位)" }`
- **响应**：`{ "message": "密码修改成功" }`
- **错误**：400 原密码错误，401 未登录，422 新密码不足 6 位
- **说明**：⚠️ 待改进：未校验新旧密码不能相同


### POST /api/reset-password — 找回密码

- **请求**：`{ "userName": "str", "newPassword": "str(6-128位)" }`
- **响应**：`{ "message": "密码重置成功" }`

## 评论模块 API 说明

### POST /api/comments — 发表评论

- **请求**：需登录 token，body：`{ "targetType": int(0商品/1猫咪), "targetId": int, "content": "str(≥1字)" }`
- **响应**：`{ "commentId": int, "targetType": int, "targetId": int, "userId": int, "userName": str, "content": str, "publishTime": datetime, "auditStatus": 0 }`

- **请求**：无请求体，公开接口。查询参数 `?targetType=0&targetId=1&skip=0&limit=20` 全部可选
- **响应**：`{ "total": int, "items": [CommentResponse] }`，每个含 userName（通过 `comment.user.userName` 链式获取）
- **说明**：只展示 auditStatus=1（已通过审核）的评论。targetType 和 targetId 需同时传入才启用联合筛选（单独传一个无效），按 publishTime 降序排列


### PUT /api/admin/comments/{comment_id}/audit — 审核评论（管理员）

- **请求**：需管理员 token，路径参数 comment_id，body：`{ "auditStatus": int(1通过/2拒绝) }`
- **响应**：更新后的评论对象
- **错误**：401 未登录，403 非管理员，404 评论不存在
- **说明**：auditStatus 只能设为 1 或 2（Schema 校验 ge=1 le=2），不接受 0。审核后评论即时生效/隐藏


### DELETE /api/comments/{comment_id} — 删除评论

- **请求**：需登录 token，路径参数 comment_id，无请求体
- **响应**：`{ "message": "评论已删除" }`
- **错误**：401 未登录，403 `"无权删除此评论"`，404 评论不存在
- **说明**：双重权限校验：`comment.userId == current_user.userId`（作者本人）或 `current_user.userType == 1`（管理员）。其他人删别人评论返回 403

#### 评论模块与前几个模块的写法差异
- **手写响应构造**：之前用 `model_validate` 一行转响应。评论响应需要 `userName`，但 Comment 表只有 `userId`，需通过 `c.user.userName` 跨表取，所以手写了 `_make_comment_response`
- **手动校验目标**：comment 的 `targetType+targetId` 指向商品或猫咪两张表，无法建单一外键，用 `_resolve_target` 在应用层校验
- **双人删除权限**：作者或管理员都能删，用 `and` 判断（userId 不匹配 **且** 不是管理员 → 才拒绝）

## 订单模块 API 说明

订单状态码：0=待处理 / 1=已支付 / 2=制作中 / 3=已完成 / 4=已取消

支付方式：0=微信 / 1=支付宝 / 2=会员卡

### POST /api/orders — 下单

- **请求**：需登录 token，body：`{ "items": [{ "productId": int, "productQuantity": int }], "paymentMethod"?: int(0-2), "userPhone": "str", "userName": "str", "orderNote"?: "str" }`，items 至少 1 个
- **响应**：`{ "batchNo": str, "userId": int, "orderStatus": 0, "paymentMethod": int|null, "orderTime": datetime, "userPhone": str, "userName": str, "orderNote": str|null, "totalAmount": Decimal, "items": [OrderDetailItem] }`
- **错误**：400 商品已下架/库存不足，401 未登录，404 商品不存在
- **说明**：自动生成 16 位 batchNo 串联多商品，逐商品校验后在一次 `commit()` 中扣库存。总金额为各商品 `price × quantity` 之和

### GET /api/orders — 查看我的订单

- **请求**：需登录 token，查询参数 `?orderStatus=0&keyword=猫&skip=0&limit=20` 可选
- **响应**：`{ "total": int, "items": [BatchOrderResponse] }`，同批次的商品行聚合为一个 BatchOrderResponse
- **说明**：keyword 通过 LEFT JOIN 查 product 表按商品名模糊匹配。`_group_by_batch` 按 batchNo 分组，`seen_batches` 去重保证列表不重复。返回按 orderTime 降序

### GET /api/orders/{order_id} — 订单详情

- **请求**：需登录 token，路径参数 order_id
- **响应**：BatchOrderResponse（含批次内所有商品明细）
- **错误**：401 未登录，403 `"无权查看此订单"`，404 订单不存在
- **说明**：权限：`userType==1`（管理员）或 `order.userId == current_user.userId`（订单所属人）。自动展开同批次所有商品

### PUT /api/orders/{order_id} — 修改订单

- **请求**：需登录 token，路径参数 order_id，body：`{ "orderStatus"?: int(0-4), "userPhone"?: str, "userName"?: str, "orderNote"?: str }`
- **响应**：更新后的 BatchOrderResponse
- **错误**：400 顾客改非待处理订单，401 未登录，403 无权修改/无权改状态，404 不存在
- **说明**：**顾客**只能改联系方式/备注，且仅限 orderStatus=0；**管理员**改状态时自动记录时间戳（设为已支付→`paymentTime`，设为已完成→`completionTime`），设为已取消→调用 `_restore_stock` 恢复库存

### DELETE /api/orders/{order_id} — 删除订单

- **请求**：需登录 token，路径参数 order_id
- **响应**：`{ "message": "订单已删除" }`
- **错误**：400 顾客删非终态订单，401 未登录，403 无权删除，404 不存在
- **说明**：**顾客**只能删已完成(3)或已取消(4)；**管理员**删非终态订单前先 `_restore_stock` 恢复库存。注意：`db.delete(order)` 只删当前这一行，同批次其他行不受影响


### 订单模块核心设计

- **batchNo 批次机制**：一次下单多商品 → 同一个 batchNo，多条 Order 行。列表/详情按 batchNo 聚合为 `BatchOrderResponse`（含 items 明细 + 总金额），避免用户以为一笔单对应一行
- **库存流转**：下单扣库存（`product.stockQuantity -= quantity`）→ 管理员取消/删除时 `_restore_stock` 恢复。顾客取消通过管理员改状态间接触发
- **defaultdict**：`_group_by_batch` 用 `defaultdict(list)` 按 batchNo 分组，不存在的 key 自动创建空列表，不需要手动判空初始化
- **快照字段**：`userPhone`/`userName` 存在 order 表而非 JOIN user 表，防止用户修改个人信息后历史订单信息跟着变。写入时从 OrderCreate 取，和下单时的信息一致

## 软引用清理修复（2026-05-21）

`comment.targetType + targetId` 和 `likes.likeType + objectId` 是软引用，数据库不会自动级联删除。本次补齐应用层清理逻辑：

- 删除评论：同步删除 `likeType=1 && objectId=commentId` 的点赞。
- 删除猫咪：同步删除猫咪本身点赞、猫咪下评论、以及这些评论上的点赞。
- 删除商品：无历史订单硬删时，同步删除商品本身点赞、商品下评论、以及这些评论上的点赞。
- 删除商品但存在历史订单时：仍按原规则改为 `status=0` 下架，同时清理商品点赞、商品评论、评论点赞。
- 删除/注销用户：删除用户评论前，先清理别人给这些评论点过的赞，避免残留点赞指向已删除评论。

新增 `backend/cleanup.py` 统一封装软引用清理 helper；未修改数据库结构，`init.sql` 和 ORM 字段保持不变。
